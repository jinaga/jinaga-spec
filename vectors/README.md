# Conformance vectors

Generated by `lake exe vectors`. Do not edit by hand: change `JinagaSpec/Cases.lean`
and regenerate. `scripts/verify.sh` fails if these files are out of date.

## `split/<name>.json`

```jsonc
{
  "name": "several-paths-each-walk-predecessors",
  "description": "What the case exercises.",
  "source": "#231, formulation A",       // where it came from
  "specification": { ... },              // input, in jinaga.js's JSON shape
  "text": "(p1: Link) { ... }",          // the same, in Jinaga's text form
  "expected": {
    "head": { ... } | null,              // null when the split has no head
    "tail": { ... } | null,              // null when the whole specification is the head
    "headText": "..." | null,
    "tailText": "..." | null,
    "tailReadsGiven": false              // is the rule's own given (given[0]) a tail given?
  }
}
```

`expected` is `splitBeforeFirstSuccessor`, the split `split_correct` is stated
for. A port of that split passes a vector when its split deep-equals
`expected.head` and `expected.tail` (a missing head or tail is `null`), and, if
it has a text printer, when printing the input, the head, and the tail gives
`text`, `headText`, and `tailText`.

`expected.tailReadsGiven` is whether the tail's givens include the specification's
own first given (`given[0]`): the shape `AuthorizationRuleSpecification`'s
constructor in `jinaga.js` refuses, because that given is the fact under
authorization, absent from the store when the rule runs (`docs/contracts.md`,
`Store.lean`). A port that builds an authorization rule (not just a split) should
throw exactly when this is `true`.

`tailReadsGiven` stays `true` for a rule that walks the given's predecessors
inside a negative existential condition, or seeks the given's successors. It is
`false` for `existential-reads-the-given`, formulation D of jinaga/jinaga.js#231:
the walk to the parent's workspace sits inside a positive existential
condition, so the split hoists it into the head.

The JSON shapes are those of `Specification` in `jinaga.js`
(`src/specification/specification.ts`). Here givens carry `conditions: []`: the
split does not take conditions on givens yet. Inverse vectors may carry them
(below).

## `well-formed/<name>.json`

The same envelope, for the check `isWellFormed`:

```jsonc
{
  "name": "projection-names-an-undefined-label",
  "description": "...", "source": "...",
  "specification": { ... }, "text": "...",
  "expected": { "scoped": true, "unshadowed": true, "projected": false, "wellFormed": false }
}
```

A port passes when its check returns exactly `expected` for `specification`. The
three verdicts are the conditions in `docs/contracts.md`. Each case states the
verdict a reader of the rules expects, and the generator refuses to write a
vector where the oracle disagrees.

## `inverse/<name>.json`

The inverse algorithm `candidates` (`JinagaSpec/Reorder.lean`), on a
specification, a graph, the subscription's givens and a fresh fact, or a fresh
batch of facts. Generated from `JinagaSpec/InverseCases.lean` (named cases) and
from fixed random seeds (`random-<n>` for single facts, `random-batch-<n>` for
batches of three).

Between them the vectors show every shape in `inverseCoverage` (`Vectors.lean`):
`exists` and `notExists` conditions, an existential condition with several
matches, one inside another, several givens, a composite projection, a batch
of several facts, a batch that holds one of the subscription's givens, and an
inverse that cannot be reordered, and a condition on a given. `lake exe
vectors` refuses to write a set that lacks one, so reseeding the generator
cannot drop a shape.

A vector whose givens carry conditions also has `expected.reduced`: the
specification with those conditions moved onto a new first match, bound to the
first given that has any, and labelled with the first of `given`, `given2`,
`given3`, ... that the specification does not name
(`reduceGivenConditions`, `JinagaSpec/GivenConditions.lean`). Its inverses are
the reduced specification's. A replica reads nothing while a condition on a
given fails.

Results are what a replica reads (`Specification.read`): none until every
given is a fact the graph holds, then `evaluate`. `gained` and `lost` compare
those reads. The random vectors draw their givens from `graph`, so a given
arrives only in the named cases `given-arrives` and
`given-arrives-under-not-exists`.

```jsonc
{
  "name": "exists-not-exists-removes",
  "description": "...", "source": "jinaga/jinaga.js#338",
  "specification": { ... }, "text": "...",
  "rowLabels": ["u1"],                  // the projection's labels: a row lists their fact ids, in this order
  "givens": { "p1": 0 },                // the subscription's givens, by label, as fact ids
  "graph": [ { "id": 0, "type": "Root", "predecessors": [] },
             { "id": 1, "type": "Account", "predecessors": [ { "role": "root", "id": 0 } ] },
             { "id": 2, "type": "Mirror", "predecessors": [ { "role": "account", "id": 1 } ] } ],
  "fact": { "id": 3, "type": "Retired", "predecessors": [ { "role": "mirror", "id": 2 } ] },
  "expected": {
    "gained": [ [ ... ] ],              // rows in the result after the facts arrive and not before
    "lost": [ [ ... ] ],                // rows in the result before and not after
    "inverses": [ { "specification": { ... }, "text": "..." } ],   // step 1, in order
    "reordered": [ { "specification": { ... }, "text": "..." } ],  // step 2: each of step 1, reordered, in order
    "candidates": [ [ ... ] ],          // every row the inverses find, given each new fact, read on the graph with all of them
    "exact": { "adds": [ [ ... ] ], "removes": [ [ ... ] ] }  // only when the projection names every top-level unknown
  }
}
```

A vector has either `fact` or `batch`. A batch vector replaces `fact` with
`"batch": [ { ... }, ... ]`: several facts saved together, each new to `graph`,
any of which may name another, listed in no particular order. A batch of one is
written as `fact`. `gained` and `lost` are the net change, from `graph` to
`graph` plus the whole batch: a row gained and lost within the batch is in
neither, and may still be a candidate.

Each inverse is an ordinary specification whose givens are the
subscription's givens followed by `__f`, a new fact. It is read once for each
new fact, starting from the subscription's givens and that fact, on the graph
that holds every new fact. A new fact that is one of the subscription's
givens was not stored before, so for it every row read on that graph is a
candidate. `candidates` is the set of rows all of those reads find, and
contains every row of `gained` and `lost` (`candidates_complete`).
A fact's `predecessors` lists one entry per predecessor; a role may appear
more than once.

`expected.exact` gives the changes of the exact inverses (`changes`,
`JinagaSpec/Exact.lean`), each read once with no re-check: `adds`, every row
the add inverses (the inverses for gained rows, with the specification's
top-level conditions re-attached) find, and `removes`, every row the remove
inverses (the inverses for lost rows, each with one top-level existential
condition flipped) find. Every row of `gained` is in `adds` and every row of
`lost` in `removes`; every row of `adds` is in the result on the new graph,
and no row of `removes` is (`exact_correct`). Within a batch, a row may be
both gained and lost and so appear in `removes` though no reader held it:
removing it changes nothing. The field is present only when the projection
names every top-level unknown (`projectsUnknowns`), the case the theorem
covers; `projection-drops-unknown` shows why. A vector usually changes the
result, but three named cases do not, and show the exact inverses holding
back a row the plain inverses find: `exists-not-exists-second-mirror` (no
remove), `not-exists-not-exists-second-freeze` (no add) and
`projection-drops-unknown` (outside the hypothesis, so it has no `exact`).

`ports/typescript/run-inverse-vectors.ts` (`npm run inverse`) checks, for each
vector:

1. jinaga.js's `MemoryStore` reads `expected.inverses` and
   `expected.reordered`, given each new fact, and jinaga.js's
   `givenCandidateInverse` for a new fact that is a given, to exactly
   `expected.candidates`. Fact ids become hashes `h<id>`.
2. If jinaga.js has `src/specification/inverse-candidates.ts`, its
   `buildInverses` of `expected.reduced`, or of `specification` when there is
   none, deep-equals `expected.inverses`; its `reduceGivenConditions`, if
   exported, gives `expected.reduced`; and
   `reorderInverse` of each deep-equals `expected.reordered`, and so does
   `candidateInverses(specification)`, the entry point jinaga.js's observer
   calls.
3. Today's `invertSpecification`, for information: on which vectors its "add"
   inverses miss a gained row, or its "remove" inverses a lost one.

## `cascade/<name>.json`

A pipeline of `@jinaga/cascade-core`, the operations a caller performs, orders
to perform them in, and the output. Generated from
`JinagaSpec/Cascade/Cases.lean`. The output is the model's denotation of what
the input holds after the operations; the steps' events reach it
(`run_correct`, `ops_correct`), whatever the order.

```jsonc
{
  "name": "group-sum-count",
  "description": "...",
  "pipeline": {
    "root": "rows",                       // createPipeline's root scope name
    "source": {                           // createPipeline's source scalars and arrays
      "scalars": [ { "name": "cat", "type": "string" }, { "name": "v", "type": "number" } ],
      "arrays": [ { "name": "bookmarks", "type": { "scalars": [ ... ], "arrays": [ ... ] } } ]
    },
    "steps": [                            // builder calls, in order
      { "step": "groupBy", "by": ["cat"], "as": "groups" },
      { "step": "sum", "array": "rows", "property": "v", "as": "total" }
    ]
  },
  "ops": [                                // what the caller does
    { "op": "add", "path": [], "keys": ["1"], "props": { "cat": "a", "v": 5 } },
    { "op": "add", "path": ["bookmarks"], "keys": ["1", "2"], "props": { ... } },
    { "op": "remove", "path": [], "keys": ["1"], "props": { ... } }
  ],
  "orders": [ [0, 1, 2], [2, 0, 1] ],     // each a permutation of the ops' indices
  "expected": [ ... ]                     // the output's root rows, as toPipelinePlainOutput gives them
}
```

An op at the root (`path: []`) is `pipeline.add(keys[0], props)` or
`pipeline.remove(keys[0], props)`. An op on a source array is
`pipeline.collection(...path).add(parentKeyPath, key, props)`, where `key` is the
last of `keys` and `parentKeyPath` the rest. An op with a `source` is on a
secondary pipeline's input, `pipeline.sources[source].add(keys[0], props)`, at
its root. A remove carries the props its row was added with, which `remove`
takes.

The steps: `groupBy` (`by`, `as`: the new root scope's name; the rows go below
each group in an array named for the scope they came from; below the root, `as`
replaces the scope's array in each of its parents), `sum`, `min`, `max`
(`array`, `property`, `as`), `count` (`array`, `as`), `dropProperty`
(`property`), `flatten` (`parent`, `child`, `as`), and `filter` (`predicate`:
`{ "op": "gt" | "lt" | "eq", "property", "value" }`, a comparison of a root
row's property with a constant; the property is the filter's mutable
property). `groupBy`, `flatten` and `filter` carry a `scope`, the array path
they run below: a port calls `.in(...scope)` before the step when it is not
empty. `defineProperty` (`as`, `expr`, `deps`) is
`.defineProperty(as, row => expr, deps)`, where `expr` is `{ "op": "prop",
"property" }`, `{ "op": "lit", "value" }`, `{ "op": "add", "left", "right" }`
(the sum of two numbers, undefined otherwise), or `{ "op": "cond", "predicate",
"then", "else" }` (a predicate as `filter`'s). `cumulativeSum` (`array`, `orderBy`, `properties`) and
`replaceToDelta` (`entity`, `event`, `orderBy`, `properties`, `outputs`) order
siblings by their `orderBy` values in turn, then by key. `pickByMin` and `pickByMax`
(`array`, `property`, `as`) give each parent a copy of the child with the least
or greatest `property`, ignoring children without one. `enrich` (`source`,
`pipeline`, `primaryKey`, `as`, and `whenMissing` when there is one) is
`.enrich(source, secondary, primaryKey, as, whenMissing)`, where `secondary` is
built from `pipeline` (`root`, `source`, `steps`) as the vector's own pipeline is.
Each root row holds as `as` a copy of the secondary's root row whose collection
key, from its root `groupBy`, matches its `primaryKey` values, or `whenMissing`.
A copied row's arrays are plain arrays, as `toPipelinePlainOutput` gives them
(jinaga/jinaga-cascade-core#43).

A port passes a vector when, for every order, its output equals `expected` up to
the order of each of the tree's arrays, those its descriptor declares in a row
or in an object, with an
empty one taken as absent: the model's arrays have no order, and none without
items. A property's value is compared as it is, a list in its order. The source descriptor names
every property the ops carry, so the pipeline's descriptors are complete.

`lake exe vectors` refuses a case whose orders disagree, or that leaves what the
model and `@jinaga/cascade-core` are meant to agree on: a summed child that
lacks the summed property or whose value is not a number (the TypeScript
converts strings with `Number()`, the model counts them 0), an integer, given or
computed, outside JavaScript's safe range, or a flattened child whose names or arrays' names
include a name its parents carry in any input the operations pass through,
since a descriptor declares every name a row ever carried. It also refuses an
ordered step whose siblings would compare by anything but their values: an
`orderBy` value absent, or not of one type, numbers or strings, across the
level (jinaga/jinaga-cascade-core#39), a summed or subtracted value that is not a number, or two siblings with the same values,
since the model and the TypeScript break ties by different orders of keys. A
pick's compared values must be numbers, since the TypeScript converts a string
with `Number()`, and no two children of a parent may tie. A secondary
pipeline is checked as the vector's own pipeline is, and its root rows must
differ in their collection key: where several match, the model gives
`whenMissing` and the TypeScript the last it saw. A secondary pipeline may not enrich in turn:
an op names one source, and a source's own sources are not modelled. A
defined property's expression may read a property its `deps` leave out only if
that property keeps one value on each row: the TypeScript recomputes only when
a dependency changes. A scoped `filter` must be the last step, since the
builder stays in the scope after it.

`lake exe vectors` also refuses to write the cascade vectors unless each of
its mutants is caught. A mutant is a deliberately broken step, such as a `sum`
that counts, a `filter` that keeps what it should drop, or a `cumulativeSum` in
the reverse order. It is caught when, in some case that uses the step, it
changes the expected output or the case is refused. A port with the same bug
then fails a vector. Steps inside an `enrich`'s secondary pipeline are not
mutated.

`ports/typescript/run-cascade-vectors.ts` (`npm run cascade`, with
`CASCADE_CORE` pointing at a checkout) runs them.
